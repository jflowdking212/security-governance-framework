# AI agent, tool and retrieval security supplement

**Status:** Supplemental implementation guidance  
**Applies to:** LLM applications, coding agents, autonomous agents, RAG systems, MCP/tool integrations, browser/computer-use agents and AI-enabled workflows  
**Related modules:** M03, M04, M08, M09, M10, M11, M12, M22  
**Reviewed:** 2026-11-18

M11 identifies the major AI/LLM security domains. This supplement turns those domains into concrete architecture, implementation and test requirements. It does not claim that prompt filtering can make an LLM immune to prompt injection.

## 1. Trust boundaries and instruction hierarchy

Treat all user messages, repository files, code comments, issue text, emails, web pages, documents, OCR output, retrieved chunks, vector metadata, tool results, model output and persistent memory as untrusted data unless independently authenticated and authorised for the specific use.

- Separate trusted system/developer policy from untrusted content in the application architecture and prompt construction.
- Label and delimit retrieved or tool-provided content as data, not as instructions. Delimiters and role labels improve clarity but are not an enforcement boundary.
- Never allow content from a repository, web page, document, email, database row or tool response to modify tool permissions, system policy, identity, approval requirements or the allowed action set.
- Do not rely on keyword filters, regexes, a second LLM or model refusal text as the security boundary. These may provide detection or defence in depth only.
- Preserve provenance for every retrieved item and tool result: source, tenant, owner, access decision, timestamp and transformation history.
- Treat multimodal extraction, OCR, document metadata, hidden text and image content as untrusted input. If the extraction process cannot preserve enough provenance or visibility context, mark the evidence incomplete.

## 2. Tool registry and execution gateway

The model may propose a tool call. A separate deterministic execution layer must decide whether that call is allowed.

- Use a server-controlled allowlist of tool names, versions and permitted operations. Do not execute arbitrary tool names, URLs, shell commands or code selected by the model.
- Give each tool a strict input schema. Reject unknown fields, invalid enums, excessive lengths, malformed identifiers and ambiguous values.
- Re-derive the caller identity, tenant, roles and session from trusted server-side context at execution time. Do not trust identity or permission claims generated by the model or copied from retrieved content.
- Enforce authorization for the specific operation, object, tenant and property immediately before the side effect. A model's plan or a previous permission check is not sufficient.
- Use least-privilege credentials scoped to the tool, tenant, environment and operation. A read-only task must not receive write credentials.
- Keep provider secrets outside prompts and model-visible context. The tool gateway should perform the authenticated operation without returning raw credentials to the model.
- Apply per-tool rate, concurrency, time, result-size and monetary limits. Add idempotency controls for tools that create or mutate external state.
- Restrict outbound network access. Apply the SSRF supplement to URL-fetching tools and prevent tools from reaching cloud metadata or internal administration services unless explicitly required.
- Isolate code execution, shell access, browser automation and file operations in a sandbox with explicit filesystem, process, network and time limits.
- Treat tool output as untrusted when it returns to the model. A tool result must never be able to grant itself additional permissions.

## 3. Human approval for consequential actions

Approval must be enforced by the execution system, not requested only in natural language.

- Classify actions by impact using deterministic policy. Examples include external communications, financial transfers, refunds, credential changes, production deployments, destructive data operations, permission changes and access to highly sensitive records.
- Require human approval before high-impact actions when the project policy requires it. Read-only or low-risk actions should not create unnecessary approval fatigue.
- Present the exact action, target, environment, affected records, arguments, expected consequence and relevant evidence to the approver.
- Bind approval to the exact proposed operation and canonicalised arguments, authenticated approver, target resource, environment, expiry and a single-use nonce or equivalent replay control.
- Revalidate the user's authority, session and resource state when approval is consumed. Reject approvals after material argument changes, role changes, session revocation, expiry or replay.
- Do not treat a broad approval such as "continue", "do what is necessary" or "approve the plan" as approval for unknown future operations.
- Record the approver, decision, action digest, time, execution result and any failure. Approval records must be tamper-evident and accessible for audit.
- Provide a cancellation path for pending operations where the external system permits it. Do not claim cancellation succeeded until the provider's authoritative state confirms it.

## 4. Retrieval-augmented generation and tenant isolation

RAG systems create a data-access boundary in addition to a model-quality problem.

- Enforce tenant and user authorization before retrieval and again before returning retrieved objects to the model. Do not rely only on a client-supplied tenant filter.
- Partition vector stores, namespaces, document stores and caches by tenant or apply equivalent server-enforced access controls.
- Include tenant and authorization context in cache keys. Never reuse a cached retrieval result across principals unless the access policy proves it is safe.
- Apply document ACLs to chunks and derived representations. Re-check access when source permissions change or documents are deleted.
- Validate source provenance, owner, ingestion time, content type and integrity before indexing.
- Treat retrieved instructions as untrusted. Retrieved text cannot override the system policy or authorise tools.
- Prevent data poisoning by controlling who can add, update, delete or re-embed documents. Keep an audit trail of ingestion and re-indexing.
- Apply chunk-size, document-size, embedding-request, retrieval-count and context-window limits.
- Avoid returning hidden, deleted, stale or unauthorised chunks from vector indexes, caches, replicas or summaries.
- Test cross-tenant retrieval with adversarial identifiers and semantically similar content, not just exact tenant ID filters.

## 5. Model output and downstream execution

Model output is untrusted input to every downstream component.

- Validate structured output against a strict schema and semantic business rules before use.
- Use allowlists for operation names, enum values, file paths, resource IDs and permitted destinations.
- Never evaluate model-generated source code, SQL, shell commands, templates or expressions in a privileged process.
- Use parameterized queries and safe rendering. Escape HTML/Markdown for the actual output context.
- Validate file paths against a fixed workspace root and prevent traversal, symlink escapes and writes outside the authorised workspace.
- Verify calculations, financial values, tax values, identity claims and security-sensitive facts using deterministic code or authoritative sources.
- Do not let the model create or modify its own policy, tool registry, approval requirements or audit records.
- When the model is uncertain or sources conflict, return an explicit unknown or request review instead of inventing authoritative facts.

## 6. Memory, state and multi-step execution

- Give memory explicit read and write permissions. Separate user, project and tenant memory and apply access checks on every read.
- Do not treat remembered content as verified truth or as a higher-priority instruction.
- Store provenance, timestamp, owner, retention and deletion metadata for persistent memory.
- Prevent one user's or tenant's conversation, files, tool output or retrieval state from entering another user's context.
- Bound agent loop depth, total model calls, tool calls, elapsed time, context growth and accumulated cost.
- Persist multi-step state with integrity protection. Resume only from validated state and re-check permissions before each side effect.
- Detect repeated failures, circular tool use, runaway retries and unexpected changes in action patterns. Stop safely when budgets or policy thresholds are reached.

## 7. Provider, model and supply-chain governance

- Record the provider, model identifier/version, endpoint, region where known, data retention and training settings, enabled tools and applicable contract terms.
- Review provider changes, model migrations, new tool integrations, MCP servers, plugins, extensions and embedding models as supply-chain changes.
- Do not send secrets, regulated data or customer content to an external provider until the data-flow, contractual, privacy and security review is complete.
- Use provider-supported structured outputs and safety features as additional controls, not as authorization.
- Define behaviour for provider outage, timeout, refusal, malformed output and fallback. A fallback model must not silently receive broader data or permissions.
- Pin versions where the provider supports it and test model changes against the same security and quality regression corpus.

## 8. Monitoring and incident response

Log security-relevant metadata such as request and trace IDs, tenant, model/provider version, retrieval source IDs, tool name, authorization decision, approval reference, policy outcome, latency, resource consumption and error category.

Do not log raw API keys, bearer tokens, passwords, full sensitive prompts, private documents or unnecessary personal data. Use protected, access-controlled evidence stores for any content retention that is justified.

Define response procedures for prompt-injection incidents, cross-tenant retrieval, secret disclosure, unauthorized tool execution, provider compromise, poisoned documents, runaway spend and model/provider outages. Preserve evidence without re-exposing sensitive content.

## 9. Required security test matrix

Use dummy data, test tenants and instrumented tool substitutes. Never place real credentials or production personal data in an attack corpus.

| Test | Required outcome |
|---|---|
| Direct prompt injection requests policy override or secret disclosure | No policy change, secret disclosure or unauthorised action |
| Indirect injection inside repository, web page, email, PDF, image OCR or tool output | Content remains untrusted data; no permission or instruction escalation |
| Retrieved malicious text asks the agent to call a tool | Tool gateway independently rejects unauthorised calls |
| Cross-tenant retrieval and cache collision | No foreign tenant data reaches the model or user |
| Revoked document access or deletion | Stale chunks, caches and summaries are not returned |
| Model proposes an unknown tool or extra schema field | Execution gateway rejects it |
| Model changes tool arguments after approval | Approval digest mismatch rejects execution |
| Approval replay, expiry or approver role revocation | Execution is rejected |
| User session expires between planning and execution | Sensitive tool call is rejected or requires re-authentication |
| Tool output contains instructions to call another tool | Returned content cannot expand tool authority |
| Output contains HTML, SQL, shell or path traversal payloads | Downstream validators/encoders prevent execution |
| Repeated tool loops or oversized context | Defined budgets stop the run safely |
| Provider outage or malformed output | No unsafe fallback, privileged default or unverified action |
| Logging and tracing | Secrets and unnecessary sensitive content are absent |

For each test, record the model/provider version, tool registry version, prompt and policy version, test input channel, expected outcome, actual tool calls, state changes and evidence. A final refusal message does not prove that no tool action occurred.
